# ZENIX-Pro business simulation and tenant isolation audit — 2026-11-14

## Scope and result

The current frontend demo was exercised in an isolated Playwright browser context against a production Vite build. The platform ticket gate, first-owner registration, additional-company registration, Admin user workflow, role sign-in, two-way UI data visibility, customer CSV exports, foreign-ID domain calls, and logout/relogin were checked. No real user data or production credential was used. The test context was closed after the run; these are reproducible test businesses, not persistent accounts in a shared service.

**Result:** the tested UI paths and domain calls did not mix A and B records. This is **not production-grade tenant security**. Both company states live in the same browser origin's `localStorage`; while signed into A, the test could read B's raw state from storage. A user with DevTools can read or alter it directly. A backend must enforce tenant membership and record scope on every request and export.

## Platform access and business setup

There is no standing Super Admin username/password in the repo. The supported `/platform` operator login uses an offline-provisioned ECDSA P-256 key and a short-lived signed ticket (`docs/AUTH.md`, `scripts/platform-provision.mjs`). The test used actor `qa.platform` and a throwaway key generated by `playwright.config.ts`; no reusable ticket or private key is included here. The real platform **Yangi kompaniya** dialog links to `/register`. It cannot create an owner password or ERP workspace itself, and there is no invite flow.

Registration has no industry field, so “Manufacturing” is a test description, not stored metadata.

All owner and employee login names/passwords were generated per run. Sampled temporary passwords were changed at first login. They are not retained as usable credentials after the isolated context closes.

## Isolation and consistency evidence

- B's direct Sales URL using an A order ID did not open a record. B's customer and LOT searches returned no A records; A's customer search returned no B customer.
- B's customer CSV contained Demo B Buyer and no A customer. A's customer CSV contained its own customer and no Demo B Buyer. Other export types were not individually inspected in this two-company run.
- After refresh and logout/relogin, the active tenant and visible state were correct in both directions. The SaaS store held ten A memberships (owner plus nine accounts) and one B membership.
- Direct domain calls using foreign supplier, customer, product, material, BOM, PO, SO, production, quality, maintenance and LOT IDs refused edits/deletes without changing the supplied state. Foreign sales-order, purchase-order, and customer-payment references also refused. These are current-state lookups, not server authorization.
- The existing `tests/ui/tenant.test.tsx` exercises the **actual tenant switch** for an account with two valid memberships, including a provider remount, state-key independence, and stale form protection. The two owners in this run each had only one membership, so their UI correctly offered no cross-company switch.
- The 506-test domain suite includes the connected Sales → MRP → PO → receipt → QC → MO → Shop Floor → final QC → delivery → return chain and checks stock movements/balances, reservations, receipts, payables/receivables, consumption, finished output, costs, references, persistence and idempotency. These checks passed; they do not substitute for server-side transactional checks.

The complete desktop E2E suite separately passed UI flows for purchase request submission, three-way invoice matching/payment, partial receipt/QC, stock transfer/count, production shop floor, serial delivery, CAPA/maintenance, finance, role restrictions, search, and subscription changes. Those tests use independent fixtures; do not read their success as one uninterrupted A-company transaction chain.

## Gaps and release meaning

1. Platform operators cannot directly create a business owner, issue an invite, or assign an industry. The supported path is owner self-registration.
2. A's structure, supplier bank details, materials, BOMs and history were loaded via a test-only fixture; this audit did not create each of those rows through the UI. The Business Admin and nine accounts, plus B's customer, were created through the UI.
3. A/B checks covered customer exports and selected searches/routes, and sampled four role logins. Every report/export type and every role-action pair was not retested in this two-company scenario.
4. There is no real billing, payment verification, email/SMS delivery, or backend session and tenant enforcement. Frontend storage is directly readable and writable by a browser user. This is a release blocker for production multi-tenant use, regardless of the passing demo checks.
